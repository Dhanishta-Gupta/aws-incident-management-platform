# AWS Services

This document describes the AWS services used in the AWS Incident Management Platform and their role in the implemented incident workflow.

## 1. Amazon EC2

### Purpose

Amazon EC2 provides a virtual Linux server that runs the workload monitored by the platform.

### Role in this project

The EC2 instance acts as the monitored resource.

CloudWatch collects the instance CPU utilization, and a controlled CPU workload was used to test the incident detection workflow.

### Configuration used

- Ubuntu Linux
- t3.micro instance
- IAM instance role
- SSH access restricted to the configured source
- CloudWatch monitoring enabled

---

## 2. Amazon CloudWatch

### Purpose

Amazon CloudWatch monitors AWS resources and applications using metrics, logs, alarms, and other monitoring capabilities.

### Role in this project

CloudWatch monitors the EC2 `CPUUtilization` metric.

The project uses a CloudWatch alarm named:

`Incident-High-CPU`

The alarm condition is:

`CPU utilization > 70%`

for one datapoint within a five-minute evaluation period.

When the condition is met, the alarm changes from `OK` to `ALARM`.

### Real test

During the project test, EC2 CPU utilization reached approximately 99.82 percent, causing the alarm to enter the `ALARM` state.

After the CPU workload was terminated, the alarm returned to `OK`.

### CloudWatch Agent

The CloudWatch Agent was installed and configured as an exploration of additional system-level monitoring and log collection.

However, the current incident-detection workflow does not depend on CloudWatch Agent metrics. The `Incident-High-CPU` alarm uses the standard EC2 `CPUUtilization` metric provided by CloudWatch.

The additional CloudWatch Agent datapoints were not successfully verified as part of the current incident workflow.

---

## 3. Amazon SNS

### Purpose

Amazon Simple Notification Service (SNS) is a messaging service used to distribute notifications to subscribers.

### Role in this project

The SNS topic:

`incident-alerts`

receives notifications from the CloudWatch alarm.

The topic has two relevant subscribers:

1. Email
2. AWS Lambda

This allows the same incident notification to be delivered both to an operator and to an automated processing function.

### Incident flow

The CloudWatch alarm publishes the incident notification to the SNS topic.

SNS then distributes the notification to:

- The email subscriber for operator notification.
- The Lambda subscriber for automated incident processing.

---

## 4. AWS Lambda

### Purpose

AWS Lambda runs code without requiring the user to manage the underlying server.

### Role in this project

The Lambda function:

`incident-record-handler`

processes incident events received through the SNS subscription.

The function generates a structured incident record containing information such as:

- Incident ID
- Timestamp
- Severity
- Alert name
- Incident message
- Incident status

The resulting record is stored as a JSON object in Amazon S3.

The current incident records use an `OPEN` status. Improving the record to include additional CloudWatch-derived fields such as the monitored metric, threshold, observed value, and EC2 instance ID is planned for the next implementation phase.

---

## 5. Amazon S3

### Purpose

Amazon S3 provides object storage for files and other data.

### Role in this project

S3 stores incident records generated by the Lambda function.

Incident records are stored under:

`incidents/`

Each incident is stored as a JSON object.

Example:

`incidents/<incident-id>.json`

The S3 bucket is private and has Block Public Access enabled.

---

## 6. AWS IAM

### Purpose

AWS Identity and Access Management (IAM) controls authentication and authorization for AWS resources.

### Role in this project

IAM is used to control what the EC2 instance and Lambda function are allowed to access.

The EC2 instance uses an IAM role rather than storing long-term AWS access keys on the server.

The Lambda function uses a separate execution role with permission to write incident records to the required S3 location.

This follows the principle of least privilege.

---

## Service Interaction

The implemented incident-processing architecture follows this flow:

    EC2
     |
     v
    CloudWatch CPU Metric
     |
     v
    CloudWatch Alarm
     |
     v
    SNS
     |----> Email Notification
     |
     v
    Lambda
     |
     v
    S3
     |
     v
    Incident JSON Record

The CloudWatch Agent is not part of the current incident-detection path. The project uses the standard EC2 `CPUUtilization` metric provided by CloudWatch.

## Verified Test Results

The project was tested in separate stages.

### CloudWatch Incident Detection Test

A controlled CPU workload increased EC2 CPU utilization to approximately 99.82 percent.

The test demonstrated that:

1. EC2 CPU utilization increased significantly.
2. CloudWatch detected CPU utilization above the 70 percent threshold.
3. `Incident-High-CPU` entered the `ALARM` state.
4. After the CPU workload was terminated, the alarm returned to the `OK` state.

### Incident Processing Test

The SNS-to-Lambda incident processing workflow was also tested.

The test demonstrated that:

1. An incident event was delivered through SNS.
2. Lambda processed the event.
3. Lambda generated a structured incident record.
4. The incident record was stored as a JSON object in S3.
5. The stored record contained incident information including an incident ID, severity, alert information, message, and status.

These tests verified the core monitoring, notification, incident-processing, and incident-storage components.
