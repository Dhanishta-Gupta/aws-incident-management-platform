# AWS Incident Management Platform

An AWS-based CloudOps project that detects infrastructure incidents, sends alerts, processes incident events, and stores structured incident records for investigation and response.

## Project Objective

The goal of this project is to build a practical incident-management workflow using AWS services commonly used in cloud operations.

The platform is designed to:

- Monitor an EC2 instance.
- Detect high CPU utilization.
- Trigger a CloudWatch alarm when a defined threshold is exceeded.
- Send incident notifications through Amazon SNS.
- Process incident events using AWS Lambda.
- Store structured incident records in Amazon S3.
- Support incident investigation, remediation, and recovery verification.

## AWS Services Used

### Amazon EC2

Provides the compute environment that is monitored for infrastructure incidents.

### Amazon CloudWatch

Collects and monitors EC2 metrics such as CPU utilization and evaluates configured alarm thresholds.

### Amazon SNS

Provides the notification mechanism for CloudWatch alarm events and delivers incident notifications through email.

### AWS Lambda

Processes incident events received through the SNS notification workflow and generates structured incident information for storage.

### Amazon S3

Stores structured incident records generated by the incident-processing workflow.

### AWS IAM

Controls access to AWS resources using roles and permissions. IAM roles are used where appropriate to avoid embedding long-term AWS credentials in the EC2 environment.

## Incident Workflow

The incident-management workflow follows these stages:

1. The EC2 instance generates infrastructure metrics.
2. Amazon CloudWatch collects and evaluates the metrics.
3. The `Incident-High-CPU` CloudWatch alarm enters the `ALARM` state when CPU utilization exceeds the configured threshold.
4. Amazon SNS receives the alarm notification and sends an email notification.
5. SNS also invokes the AWS Lambda function.
6. Lambda processes the incident event.
7. Lambda creates a structured incident record in Amazon S3.
8. The operator investigates the affected EC2 instance using CloudWatch metrics, logs, and system-level troubleshooting.
9. Appropriate remediation is performed.
10. Recovery is verified by checking the system and monitoring state.
11. The incident can then be documented and reviewed.

The end-to-end incident-processing workflow was tested using the project environment.

A test incident was sent through the SNS → Lambda workflow, and the Lambda function successfully processed the event and created a structured JSON incident record in Amazon S3.

The generated test incident included fields such as:

- Incident ID
- Severity
- Source
- Alert
- Incident message
- Status

The test incident was successfully stored with an `OPEN` status.

The project also includes a CloudWatch alarm named `Incident-High-CPU`, configured to detect CPU utilization above 70%.

The alarm and incident-processing components were tested to verify the monitoring and automation workflow.

## Incident Response

The project includes an incident response runbook describing the operational process for:

- Receiving and acknowledging an incident alert.
- Checking CloudWatch alarms and metrics.
- Identifying the affected EC2 instance.
- Investigating system and CloudWatch logs.
- Performing safe remediation.
- Verifying recovery.
- Reviewing the incident record.
- Documenting the incident.
- Escalating incidents when required.

See `docs/incident-response-runbook.md` for the detailed response procedure.
